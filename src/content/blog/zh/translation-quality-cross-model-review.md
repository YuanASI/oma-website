一段翻译可以读起来很自然，同时悄悄改掉原意。

一个限定词消失了。一个截止日期变软了。一句产品承诺变得比原文更宽。单看译文没有问题，直到有人拿它和原始意图对照。

回译能给本地化团队一个有用信号：把译文重新翻回源语言，再看中间发生了什么变化。

如果第二遍不来自同一个模型提供方，这个信号会更有价值。

## 三个角色组成的审阅闭环

可运行的[翻译与回译示例](/zh/examples/translation-backtranslation/)把工作拆成三个角色：

1. 翻译 Agent 使用 Claude，把英文原文翻成目标语言。
2. 回译 Agent 使用另一家提供方，把结果重新翻回英文。
3. 审阅 Agent 比较原文与回译，并返回结构化的语义漂移发现。

模型是刻意混用的。回译不应只是让同一套模型偏好，再次复现第一遍措辞。

然后，Reviewer 把比较变成数据。它不只返回一句“看起来没问题”，而是指出哪里发生了意义变化，并把这些发现送进人工审阅队列。

## 回译能发现什么

这套形态适合发现这些变化：

- 否定含义消失。
- 数字、日期或单位变化。
- “必须”和“可选”互换。
- 适用范围变宽或变窄。
- 产品术语在不同段落里漂移。
- 语气变化，进而影响读者应该采取的动作。

它尤其适合重复、结构化内容：帮助中心更新、产品通知、发布沟通，以及需要人工优先级队列的批量本地化。

输出应该把人指向风险，而不是假装可以替代人。

## 它证明不了什么

一次干净的回译，不能证明目标语言文本一定正确。

两个模型可能共享同一个盲点。过于字面的回译，也可能把合理的本地化选择误报为问题。符合当地文化的表达，逐字翻回来本来就会不同。领域术语还可能依赖模型没有拿到的术语表。

所以最后一个角色叫漂移 Reviewer，不叫自动发布器。

真正的生产工作流仍然需要：

- 经过批准的术语表。
- 针对 locale 的风格规范。
- 法律、医疗、金融或安全关键内容的人工审阅。
- 一套带标注的评估集，区分合理改写与实质漂移。
- 对原文、译文、审阅发现和最终批准做版本化记录。

## 为什么多个 Agent 有帮助

这里确实存在三种不同职责：

- 产出目标语言文本。
- 创建一份相对独立的比较表面。
- 按明确 schema 判断语义差异。

把三种职责塞进一个 prompt，会拿掉这条工作流最想获得的独立性。拆成三个角色后，每次交接都可检查，每个角色也可以使用自己的模型提供方和约束。

额外调用当然有成本。对于低风险文案或一句短文本，一次翻译加人工审阅可能更简单。

只有当体量或后果值得维护一份结构化审阅队列时，才使用多智能体闭环。

## 运行跨模型 recipe

示例需要 Anthropic key 做翻译，并需要 OpenAI 或 Gemini 中至少一个，作为第二家模型提供方：

```bash
npx tsx packages/core/examples/cookbook/translation-backtranslation.ts
```

先运行随附样例。然后在原文里加入一个刻意危险的变化，例如数字、否定词或截止日期。检查结构化 Reviewer 能不能把差异暴露出来。

先建评估集，再建自动发布。
