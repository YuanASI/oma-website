很多事故复盘，是从一条糟糕的队列开始的。

一个人先看日志。然后有人检查部署历史。再然后，团队估算客户影响。等这些都做完，才终于开始解释发生了什么。

这条顺序容易管理，但大部分等待没有必要。日志、部署和影响范围是三路不同证据，完全可以同时调查。

真正重要的是下一步：在每一路都产出可追溯证据之前，不要急着把它们揉成一段故事。

## 这张任务图

可运行的[事故复盘 DAG](/zh/examples/incident-postmortem-dag/)有五个任务：

1. 日志调查 Agent 从事故日志中提取模式。
2. 部署调查 Agent 检查近期变更与事故的相关性。
3. 影响调查 Agent 分析影响范围。
4. 根因分析 Agent 等待三路调查完成，再形成有证据支撑的假设。
5. 复盘写作 Agent 把证据和假设整理成最终文档。

前三个任务互不依赖，所以同时启动。三路调查没有全部结束，分析就不能开始。分析没有完成，写作也不能开始。

这张 DAG 很小，但它编码了一条重要的操作原则：

> 证据收集并行跑，判断按顺序做。

综合开始太早，一个醒目的信号就可能主导整段叙事。所有调查都串行跑，团队又会白白付出墙钟时间。

## 让证据保持可追溯

事故复盘不只是一份写得顺的解释。它首先是一条证据链。

日志调查需要说明找到了什么模式。部署调查需要指出相关的是哪次变更。影响调查则要说清楚，随附情境能支持多大的范围判断。

下游分析 Agent 通过任务依赖拿到这些已完成结果。事后不需要再猜一句话到底来自哪个来源。

这样做还有一个好处：分歧会变得有用。日志可能指向一种故障模式，部署时间却指向另一个方向。分析 Agent 的职责，是处理这份张力，而不是把它抹掉。

## 最终交付物

这个示例会产出：

- 三路调查结果。
- 建立在这些输入上的根因假设。
- 一份最终复盘文档。
- 示例打印的运行耗时与用量信息。

它不会查询真实日志服务、部署平台、状态页或工单系统。事故情境随 recipe 一起提供。这样便于检查编排，同时也明确了证据边界。

接入真实系统是另一层工作。应用至少要决定：

- 每个调查 Agent 可以查询哪个时间窗口。
- 哪些字段在模型访问前必须脱敏。
- 客户数据是否可以离开受控环境。
- 最终文档必须保留哪些来源链接与查询参数。
- 谁来批准根因结论与纠正措施。

## 为什么这里适合显式任务图

这条工作流不需要协调器临时发明拓扑。五个角色和依赖关系，在事故开始前就已经知道。

所以显式 `runTasks()` 图更适合作为默认选择：

- 每次都运行相同的证据分支。
- 依赖关系可以在代码里审阅。
- 缺失分支会阻止综合，而不是静默消失。
- 互不依赖的分支依旧可以并行。

如果不同类型事故的调查计划差异很大，动态协调器才开始有意义。即便如此，在授予生产系统访问权之前，也应先检查它提出的计划。

## 运行这个 recipe

设置 `ANTHROPIC_API_KEY` 后，在框架仓库根目录执行：

```bash
npx tsx packages/core/examples/cookbook/incident-postmortem-dag.ts
```

先运行随附情境，检查任务记录和最终文档。然后每次只把一条证据分支替换成自己系统的只读集成。

安全的推进顺序刻意很无聊：fixture、只读来源、人工审阅结果，最后才是更大权限。
